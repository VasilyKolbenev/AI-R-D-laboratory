Первое ограниченное задание Claude Code: проверить самые важные соглашения архитектуры небольшим воспроизводимым spike до сборки полноценного продукта.

Порядок работы: пользователь вручную передаёт задание Claude Code в этом же репозитории. Claude реализует ограниченный результат и возвращает отчёт пользователю. Пользователь передаёт отчёт Codex, который проверяет код и определяет следующий шаг как технический руководитель.

01 · Прочитать перед изменениями

Рабочая директория: корень текущего checkout AI-R-D-laboratory. Прочитать CLAUDE.md в корне и существующие AGENTS.md, если появились, затем:

  • architecture.html: контракты, согласование, бюджет, состояния и границы доверия.
  • implementation-plan.html: этап P0 и выход G0.
  • experiment-plan.schema.json, example-plan.json, domain-model.json.
  • Constellation и UX-обзор: утверждённое направление интерфейса, а не работающий backend.

Зафиксировать исходный git status --short. Существующие изменения сохранить; UI и документы предложения не перезаписывать.

02 · Граница задания

Использовать Python 3.11+ и стандартную библиотеку: dataclasses, hashlib, decimal, threading, unittest. Не добавлять сервисы, зависимости и полный application scaffold. План прочитать из существующего синтетического примера; его placeholder-хеши не выдавать за проверенные артефакты. Оригинал не менять: положительные сценарии бюджета используют отдельные явно синтетические test fixtures с лимитом 100 условных единиц. Исходный пример имеет нулевой бюджет и должен отклонять положительный резерв.

Минимальный вертикальный срез

Неизменяемый снимок plan body и manifest → hash → human approval → резерв бюджета → fake-provider → результат либо неизвестный исход → reconciliation.

Остаётся за пределами

Настоящие API, ключи, платежи, Temporal, PostgreSQL, sandbox, серверная подпись, авторизация пользователей, deployment и переделка интерфейса. Их отсутствие явно указать в ADR.

04 · Что проверить

  1. Успех: резерв 100 единиц, подтверждённый расход 70, освобождение 30; повторная обработка события не списывает повторно.
  2. Отказ до отправки: подтверждённое отсутствие обращения позволяет освободить резерв; решение о повторе остаётся явным.
  3. Timeout после принятия: fake-provider мог начислить плату. Обращение ровно одно; автоматического повторного платного вызова нет. Резерв переносится в unresolved exposure без освобождения и двойного учёта.
  4. Отмена и сверка: отмена запрещает новые dispatch, но сохраняет неизвестное обязательство. Подтверждённая сверка завершает учёт; недоступная сверка оставляет сумму удержанной.
  5. Согласование: изменение данных, кода, модели, инструмента или основной метрики меняет hash и делает старое approval непригодным. Истечение срока, исчерпание числа запусков и запрос агента вместо человека отклоняются.
  6. Параллельность: два резерва по 60 при лимите 100 не проходят одновременно. Это доказательство для одного процесса с lock, не проверка PostgreSQL-транзакций.
  7. Протокол: одиночное воспроизведение допустимо; сравнению нужны минимум два кандидата и ровно один baseline. Основная метрика ровно одна; ID уникальны; лимиты попыток согласованы.

Время и ответы задаются фикстурами, без sleep. Изменение порядка JSON-ключей не должно менять hash. Правила сериализации документировать; ограниченную проверку не называть полной валидацией JSON Schema или реализацией RFC 8785.

05 · Команды и приёмка

Из корня репозитория:

git status --short
python --version
python -B -m unittest discover -s spikes/task_001/tests -v
python -B -m spikes.task_001.run_demo --scenario all --report spikes/task_001/result.json
git diff --check
git status --short
  • Все перечисленные сценарии имеют автоматические проверки, включая отрицательные исходы.
  • JSON-отчёт позволяет восстановить переходы и проверить число вызовов/условных начислений.
  • Неизвестный исход сохраняет обязательство и не создаёт скрытый повтор.
  • Изменены только файлы задания; нет сети, секретов и правок согласованного UI.
  • ADR отделяет доказанное в spike от ещё не проверенной production-архитектуры.

Это вход для ревью G0, не завершение всего G0 и не готовность этапа G3. Если обнаружено противоречие, описать его и предложить минимальное решение; не расширять задачу молча.
