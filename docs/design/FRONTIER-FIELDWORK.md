# VV Frontier: Fieldwork design study

26 October 2026. A research instrument linked from the installed Reactor at
`/workbench/`; a separate development preview remains on port8797.
Audience: an individual applied researcher deciding whether a technology
deserves a bounded experiment. The useful outcome is an inspectable decision,
not an attractive but unsupported recommendation.

## Experience

One saved study, three lenses: mechanism, comparable measurements, evidence.
Selecting a diagram node exposes its saved basis. The critic track exposes
specific objections and the editor's recorded dispositions. Memory shows the
selection frozen before approval. Costs describe the current run; cached input
is part of input, reused phases are not billed again in this display.

The visual system uses joined dark working surfaces, a paper evidence inspector,
local Manrope, a restrained acid accent and meaningful data movement. Motion
shows the stored operation sequence, never measured latency. It is manual,
finite, stops on view changes/backgrounding and respects reduced motion.

Actual missing values stay missing. Author claims and external measurements are
labelled. Only numeric pairs marked comparable with conditions and unique
evidence references can create a plot. Legacy prose is not silently converted
into measurements or verified claims. An archive connection is not independent
scientific validation. No invented customer counts, speedups or confidence scores.

## Working boundary

`deliverables/ui/frontier-instrument/preview_server.py` serves a separate local
development page on 127.0.0.1:8797. Its explicit GET proxy reads the lab on port8795.
The installed `/workbench/` serves the same UI with the main strict CSP and APIs.
There is no dispatch, save, research, queue-approval or publication operation in
the new workspace UI. Existing approval flows and approved packages remain separate. Navigation
links can open the existing working interface for the selected research.

No new research, benchmark, external model call, Telegram send or channel
publication is part of this design evaluation. Local acceptance snapshots are
kept outside the repository under the chat's outputs folder.

## What would make the public product worth installing

1. A reproducible decision package: primary-source snapshot, explicit claim
   bindings, comparison conditions, model/version metadata and the cheapest next
   falsifying experiment. Existing archive/recipe/export parts are a foundation;
   universal executable reproduction is not implemented by this UI.
2. A useful longitudinal view: which conclusions depend on a changed source and
   why they should be revisited. Existing archive impact checks are a foundation;
   continuous internet monitoring and a causal knowledge graph are not present.
3. A verifiable first-use path: independent users install, import their material,
   inspect a saved example and reach a useful next action. Measure installation
   completion, time to first useful decision, bound claims and corrections caught
   before publication. Publish real outcomes and three domain examples before
   making broad superiority claims. A ten-minute setup is a target to test.

GitHub stars are a possible distribution outcome; this study does not establish
adoption, independent research quality, or superiority over other products.
